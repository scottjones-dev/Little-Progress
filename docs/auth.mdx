# Auth (Better Auth)

This is the design for **parent accounts**. Carers use the shared PIN gate, which is a separate system (see `docs/plan.md`, "Auth and roles"). Nothing here applies to carers.

Status: **planned, not built.** Email templates already exist in `packages/emails`; the Better Auth wiring does not.

## 1. Requirements

| Need | Decision |
| --- | --- |
| Email verification | **Required** before first sign-in |
| Change email | **Not allowed.** `user.changeEmail` stays off (it is off by default) |
| Social sign-in | Google and Microsoft now. Apple later, once the Apple Developer fee is paid |
| Password reset | Email link, single use, short expiry |
| "Your password changed" email | Sent every time, whether by reset or by change in settings, so a stranger's change gets noticed |
| Account lockdown | Lock after repeated failed sign-ins; unlock by email link |
| 2FA | Authenticator app (TOTP) plus backup codes. Email OTP is optional |
| Passkeys | Optional sign-in method and a second factor |
| Last login | Show "you last used Google" on the sign-in screen, and last sign-in time in settings |

Why no email change: the email address is the identity. Fixing a typo is rare, and an attacker who hijacks a session could redirect all reset mail by changing it. If someone truly needs it, it is a manual support action (see section 8).

## 2. Constraints and scale

Primer step 1. Roughly 2 parents per family, a handful of families, so traffic is tiny. We optimise for **security and clarity**, not throughput. The data is a child's health diary, so a hijacked account is the main risk. That is why the email notices, lockout and 2FA matter more than speed.

If Novu is unreachable, the trigger call fails. Auth logs it and alerts, and the user can press "resend" (verify and reset). We do not make sign-up wait on Novu, for the timing reason in section 5.

## 3. High-level design

```
Web (Next) ─┐                         ┌─ Postgres (Drizzle): user, session, account,
            ├─ HTTPS ─▶ Hono API ─────┤   verification, twoFactor, passkey, lockout
Native      ┘   /api/auth/*           └─ @repo/notifications ─▶ Novu ─▶ email
(Expo)          Better Auth handler          (typed trigger)    (workflows)
                    │
                    └─ OAuth ─▶ Google · Microsoft · Apple (later)
```

- Better Auth is mounted in `apps/api` at `/api/auth/*`.
- Web uses cookie sessions. Native uses the Expo plugin with bearer storage in SecureStore.
- Auth **never sends email itself**. It calls `@repo/notifications` (new package, Novu), which owns delivery. Auth does not import Novu or `@repo/emails`, so providers, channels (push and in-app later) and templates can change without touching auth.
- `@repo/emails` stays the template source. Novu email steps use its built HTML with `{{payload.x}}` tokens (`EMAIL_TOKEN_PREFIX=payload.` build, see `packages/emails/README.md`).

## 4. Flows

### 4.1 Sign up and verify email

1. User enters email and password (min 8, max 128, checked against known-breached passwords, see section 6).
2. Better Auth creates the user with `emailVerified = false` and sends **verify-email**.
3. Sign-in is refused until the link is clicked. With `requireEmailVerification` on, sign-up also returns the same success response for an already-registered email, so the form cannot be used to discover who has an account.
4. Clicking the link verifies the email and signs the user in.

### 4.2 Sign in

Password, social, or passkey. After credentials pass:

1. If the account is locked, refuse (section 4.6).
2. If 2FA is on and the method is password, redirect to the 2FA screen.
3. If the sign-in is from a country we have not seen for this user, send **new-location-sign-in** (country from the `CF-IPCountry` header only, as in the plan).
4. Record the login method (section 7).

### 4.3 Forgot and reset password

1. User asks for a reset. We always answer "if that email exists, we sent a link", never confirming it.
2. **reset-password** email with a single-use link, 1 hour expiry.
3. On success: all sessions are revoked (`revokeSessionsOnPasswordReset: true`) and **password-changed** is sent.

### 4.4 Change password (signed in)

User gives current plus new password. We pass `revokeOtherSessions: true`, then send **password-changed**.

The "password changed" email must fire on **both** 4.3 and 4.4. Better Auth has `onPasswordReset` for reset only. The docs I read list no callback for change-password, so we hook the `/change-password` endpoint with an `after` hook and verify this when we build it. One shared `notifyPasswordChanged(user)` function is used by both paths, so they cannot drift apart.

The email says "if this was not you, lock your account", with a button to the lockdown link (4.6).

### 4.5 Link Google, Microsoft, Apple

- Linking is allowed from settings (`account.accountLinking.enabled`). Google and Microsoft are listed in `trustedProviders`, because they only report verified emails.
- `allowDifferentEmails` stays **false**. A linked provider must have the same email as the account. This keeps the "email is identity, cannot change" rule honest: you cannot link a different address as a backdoor.
- `allowUnlinkingAll` stays false, so a user can never remove their last way to sign in.
- A user who only ever signed in with Google has no password. They can set one through the reset flow.

**Apple, later.** Needs a paid Apple Developer Program membership. When it is paid we need a Services ID, a key, and a team ID. Apple's quirks to plan for: the user's name is sent only on the **first** sign-in (store it then), and the user may choose "Hide my email" and give us a private relay address. A relay address will not match their real account email, so Apple sign-in would be a separate account unless they link it while signed in, and that conflicts with `allowDifferentEmails: false`. Decide this when we do Apple (see open questions). Apple is also required on iOS if we offer any other social sign-in in the native app, so it blocks the App Store release, not the web.

### 4.6 Lockdown

Better Auth rate-limits requests but has **no per-account lockout**, so this is ours to build.

- Count failed password sign-ins per account. After **5** failures in 15 minutes, set `lockedUntil` and send **account-locked** email. Fixed delay first (15 minutes), not permanent, so an attacker cannot lock a victim out for good.
- The email has an **unlock** link (single use). Using it clears the counter and revokes all sessions.
- A locked account still returns the generic "invalid email or password" error, so locking is not an oracle.
- A manual **"lock my account"** link in password-changed and new-location emails sets the lock immediately, revokes sessions and forces a reset. This is the "if it was not me" path.
- IP-level limits stay in the edge and Hono rate limiter from the plan (login 5/min per IP+email). Lockout is the per-account layer under it.

Table: `account_lock(user_id pk, failed_count, window_started_at, locked_until, unlock_token_hash, unlock_expires_at)`. Only a hash of the unlock token is stored.

### 4.7 Two-factor (TOTP)

Plugin: `twoFactor` from `better-auth/plugins`.

- Enabling needs the current password and a first successful code (`skipVerificationOnEnable: false`), so a user cannot lock themselves out with a mis-scanned QR.
- 10 backup codes, shown once. Tell the user to store them.
- "Trust this device" for 30 days is allowed (`trustDevice`), because parents log in on their own phones daily.
- Users who signed up with social or passkey only cannot enable 2FA unless `allowPasswordless: true`. We keep it false: Google, Microsoft and Apple do their own MFA, and a passkey already counts as strong.
- Send a short **two-factor-changed** notice when 2FA is turned on or off (new template, see section 5).

### 4.8 Passkeys

Plugin: `@better-auth/passkey` (this is a separate package; it is not in `better-auth/plugins`).

- Needs `rpID` (our domain, no scheme), `rpName`, `origin` (our web origin). These come from `@repo/env/api`.
- Passkeys are an **added** sign-in method, never the only one at first.
- Native: the Expo client `cookiePrefix` must match the passkey challenge cookie prefix, or the flow fails.
- Passkeys are domain-bound. The domain we choose for production is hard to change later, so settle it before users enrol.

## 5. Emails

Templates live in `@repo/emails`. Delivery is a Novu workflow in `@repo/notifications`, one workflow per row below, with the same id as the template. Auth only calls:

```ts
import { notify } from "@repo/notifications";

void notify("password-changed", {
  to: { subscriberId: user.id, email: user.email },
  payload: { name: user.name, time, device, location, lockUrl },
});
```

`notify` is typed: the event id decides the payload shape, so a missing `url` is a compile error. Auth owns the links (verify, reset, unlock) because Better Auth generates the tokens; notifications only delivers them.

Novu points to keep in mind:

- The subscriber id is our `user.id`. Subscribers are created or updated on trigger, with the email from the user row.
- Security workflows (password changed, locked, new location, 2FA changed) are marked **critical** in Novu so a user's preferences cannot switch them off.
- Verify and reset must send even when the user has never set preferences, so they are also critical.
- Payloads carry the data the email needs (name, url, device, time) and nothing else. No password or token other than the one-time link.
- Novu holds a copy of recipients' emails and payloads. Note it in the privacy notice, and pick the EU region if available.

| Event | Template | Exists? |
| --- | --- | --- |
| Sign-up, resend verification | `verify-email` | Yes |
| Forgot password | `reset-password` | Yes |
| Password changed (reset or settings) | `password-changed` | Yes |
| Sign-in from a new country | `new-location-sign-in` | Yes |
| Magic link | `magic-link` | Yes, **unused** (we are not offering magic-link sign-in) |
| Account locked, with unlock link | `account-locked` | **New** |
| 2FA turned on or off | `two-factor-changed` | **New** |
| Passkey added or removed | `passkey-changed` | **New** (optional) |
| Social account linked or unlinked | `account-linked` | **New** (optional) |

Rules for every send:

- Do not `await` `notify` inside a Better Auth callback (`void notify(...)`). Waiting makes "email exists" requests slower than "email does not exist" ones, which leaks who has an account. `notify` catches and logs its own errors so a failed trigger never becomes an unhandled rejection.
- Security notices (changed, locked, new location) cannot be unsubscribed from.
- Links carry only a random token, never the email or user id.

## 6. Config sketch

A shape to build from, not final code. Check option names against the installed `better-auth` version when implementing.

```ts
// apps/api/src/auth.ts
import { betterAuth } from "better-auth";
import { lastLoginMethod, twoFactor } from "better-auth/plugins";
import { passkey } from "@better-auth/passkey";

export const auth = betterAuth({
  appName: "LittleProgress",
  emailAndPassword: {
    enabled: true,
    requireEmailVerification: true,
    minPasswordLength: 8,
    revokeSessionsOnPasswordReset: true,
    sendResetPassword: ({ user, url }) =>
      void notify("reset-password", {
        to: toSubscriber(user),
        payload: { name: user.name, resetUrl: url },
      }),
    onPasswordReset: ({ user }) => void notifyPasswordChanged(user),
  },
  emailVerification: {
    sendOnSignUp: true,
    autoSignInAfterVerification: true,
    sendVerificationEmail: ({ user, url }) =>
      void notify("verify-email", {
        to: toSubscriber(user),
        payload: { name: user.name, verifyUrl: url },
      }),
  },
  user: {
    changeEmail: { enabled: false }, // email is the identity
  },
  account: {
    accountLinking: {
      enabled: true,
      trustedProviders: ["google", "microsoft"],
      allowDifferentEmails: false,
      allowUnlinkingAll: false,
    },
  },
  socialProviders: {
    google: { clientId, clientSecret },
    microsoft: { clientId, clientSecret, tenantId: "common" },
    // apple: added when the Apple Developer account exists
  },
  plugins: [
    twoFactor({ issuer: "LittleProgress", backupCodeOptions: { count: 10 } }),
    passkey({ rpID, rpName, origin }),
    lastLoginMethod({ storeInDatabase: true }),
  ],
  // after-hook on /change-password -> notifyPasswordChanged
  // before/after hooks on /sign-in/email -> account lock counter
});
```

Password strength: also reject known-breached passwords (Better Auth has a `haveIBeenPwned` plugin; confirm it is available in the installed version).

## 7. Last login

Two separate things, both small:

1. **Last used method** (`lastLoginMethod` plugin). Stores "google" or "email" in a cookie, and in the database with `storeInDatabase: true`. The sign-in screen highlights it ("You used Google last time"). The plugin's cookie holds no secret. Under UK GDPR use the `beforeStoreCookie` hook to only set it once the user has agreed to optional cookies, or treat it as strictly necessary and say so in the privacy notice (decide with the privacy notice).
2. **Last sign-in time and place** for the settings page. Better Auth sessions already store IP and user agent. We show the session list with coarse location (country only) and a "sign out this device" button. This is the same data the new-location email uses.

## 8. Account recovery and support

- Lost password: reset link (4.3).
- Lost authenticator and lost backup codes: this is the hard case. Plan: sign in with a passkey or social login if linked, otherwise a manual support process that verifies identity out of band. Write the exact steps before launch. Do not add an email-only "disable 2FA" link, since that removes the point of 2FA.
- Wrong email at sign-up (the no-change rule): the unverified account is simply abandoned and expires after 7 days; they sign up again with the right address.
- Genuine need to change email: support deletes and recreates, or runs a one-off script after identity checks. Rare by design.
- Delete account: `user.deleteUser` with an email confirmation, tied to the plan's delete-all data export.

## 9. Data model

Better Auth owns `user`, `session`, `account`, `verification`. The plugins add:

| Table or column | From | Holds |
| --- | --- | --- |
| `user.two_factor_enabled` | twoFactor | boolean |
| `two_factor` | twoFactor | encrypted TOTP secret, hashed backup codes |
| `passkey` | passkey | public key, counter, device name |
| `user.last_login_method` | lastLoginMethod | "email", "google", "microsoft", "apple", "passkey" |
| `account_lock` | ours | section 4.6 |

Generate the Drizzle schema with the Better Auth CLI, then `pnpm db:generate` and `pnpm db:migrate`. Do not hand-write the Better Auth tables.

## 10. Secrets and environment

Add to `@repo/env/api` and Infisical (`/api`): `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`, `MICROSOFT_CLIENT_ID/SECRET`. The Novu key (`NOVU_SECRET_KEY`) belongs to `@repo/notifications`, so it lives in `@repo/env` for that package, not in auth. Later: `APPLE_CLIENT_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`. Passkey `rpID` and `origin` per environment. Redirect URIs must be registered for dev, staging and prod in each provider's console.

## 11. Threats and what answers them

| Threat | Answer |
| --- | --- |
| Stolen password | 2FA, new-location email, lockdown link |
| Attacker changes the password | password-changed email to the real owner, with lock link |
| Attacker changes the email | Not possible (feature off) |
| Password guessing | Rate limit per IP, per-account lockout, breached-password check |
| Finding who has an account | Same response for existing or new emails, same generic login error, un-awaited email sends |
| Reset link theft | Single use, 1 hour, hashed in DB, all sessions revoked on use |
| Provider account takeover via linking | Same-email rule, trusted providers only, no unlinking the last method |
| Lock someone out on purpose | Lock is temporary and unlockable by email |
| Lost 2FA device | Backup codes, passkey, manual support process |

## 12. Tests

Per project rules, tests come with the code. Vitest in `apps/api` against a real test Postgres:

- Sign-up sends verify email; unverified sign-in refused; link verifies.
- Existing-email sign-up looks the same as new-email sign-up.
- Reset: token works once, expires, revokes sessions, sends password-changed.
- Change password in settings sends password-changed (this proves the after-hook).
- 5 bad passwords lock the account; right password still refused while locked; unlock link works once.
- Change-email endpoint returns an error.
- Linking a provider with a different email is refused.
- 2FA: enable needs code; sign-in redirects; backup code works once.
- `notifyPasswordChanged` is called from both paths.

Playwright E2E later: full sign-up, verify, 2FA, passkey (virtual authenticator).

## 13. Build order

1. Install `better-auth` and the CLI generator; generate and migrate the base tables.
2. Build `packages/notifications` first (Novu client, typed `notify`, workflows for verify, reset, password-changed), then wire those three into auth.
3. Email-and-password flow with required verification and the web screens.
4. Lockout and the lock/unlock emails.
5. Google and Microsoft, plus account linking settings.
6. 2FA (TOTP, backup codes).
7. Passkeys.
8. Last login method and the session list.
9. New-location notice (needs the Cloudflare country header).
10. Native (Expo) client. Apple sign-in when the developer account is paid.

## 14. Open questions

- **Apple relay emails** vs `allowDifferentEmails: false` (4.5). Likely answer: allow Apple linking only when signed in, and accept the relay address as the Apple identity.
- Decided: delivery goes through `@repo/notifications` on Novu. Still open: Novu workflows defined in code (Novu Framework, rendering `renderEmail`) or uploaded as HTML with tokens. Code-first keeps workflows in git and is my lean.
- Which email sender sits behind Novu (Resend, SES, etc.) is Novu config, not auth's concern.
- Lockout thresholds (5 in 15 minutes, 15-minute lock) are a first guess; tune once we see real use.
- Is the last-login cookie "strictly necessary" or does it need consent? Decide with the privacy notice.
- Should 2FA be **required** for parents, given the data is a child's health record? Recommendation: strongly prompt at sign-up, make it required before the first report export or carer PIN change.
