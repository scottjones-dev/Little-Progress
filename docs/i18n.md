# Internationalization (i18next)

How text is translated on the server, the website and the app. Code: `packages/i18n` (catalogs and rules), `apps/web/src/lib/i18n`, `apps/native/src/lib/i18n.ts`, and the email and push text in `packages/emails` and `packages/notifications`.

## 1. The idea

Everything a person reads comes from translation files, never from a string in code. One library (i18next) and one file format are used on all three platforms, so a sentence is translated once.

| Where | Library | Language comes from |
| --- | --- | --- |
| Emails and push (server) | `i18next` through `getT(locale, namespace)` | the recipient's saved language (`user.locale`), sent with the notification |
| Website | `react-i18next` (Client Components), `getTranslations()` (Server Components) | cookie `lp_locale`, then the browser's `Accept-Language`, then English |
| App | `react-i18next` + `expo-localization` | the language chosen in the app, then the device language, then English |
| API errors | none | the JSON `message` stays English for developers; clients show `errors:<CODE>` for the `code` |

Languages now: English (`en`, the source), Polish (`pl`), Spanish (`es`), Welsh (`cy`). All read left to right. Catalogs use language codes; the regional flavour for dates and numbers (`en-GB`) is `app.locale` in `@repo/config`. Anything missing falls back to English, so a person never sees a raw key.

## 2. The catalogs

`packages/i18n/src/locales/<language>/<namespace>.json`

| Namespace | Holds                                             |
| --------- | ------------------------------------------------- |
| `common`  | buttons, the tagline, the language label          |
| `errors`  | one message per API error code (`@repo/errors`)   |
| `emails`  | all email text (subjects, headings, body, footer) |
| `push`    | push notification titles and bodies               |
| `shell`   | error pages and the not-found page                |

Screen namespaces (`auth`, `entries`, `reports`) are added with those features.

### Rules for writing a key

- Plain text only: no HTML or markdown. A link or button is a separate element, not part of a sentence.
- Placeholders are `{{name}}`. Never put real names, emails, child details or any personal data in a catalog: the files are sent to a translation service.
- A number that changes the wording uses plural keys: `thing_one` and `thing_other` in English. Pass `count` to pick the form and `amount` to show the number (see `packages/emails/src/lib/plural.ts`). Polish needs `_few` and `_many` too, Welsh also `_zero` and `_two`. The check script lists exactly which are missing. Where a neutral wording works ("Attempts: {{amount}}"), prefer it to a plural.
- Group keys by screen or message: `verifyEmail.heading`, `verifyEmail.button`.
- Write for the reader, short and calm. English is the source of truth.

### Using a key

```ts
// Server code (emails, push)
const t = getT(user.locale, "push");
t("passwordChanged.title");

// Website Server Component
const t = await getTranslations("common");

// Website Client Component or the app
const { t } = useTranslation("common");
```

Keys are typed from the English files, so a wrong key does not compile.

## 3. Choosing the language

`resolveLocale()` in `@repo/i18n/resolve`, in this order: the signed-in parent's saved language, the remembered cookie, the browser's `Accept-Language`, the device language, then English. Unsupported languages are skipped (`fr` becomes English; `pl-PL` becomes `pl`).

- Website: the root layout reads the cookie and header, sets `<html lang>`, and wraps the page in the translation provider. Reading them makes pages render per request, which is fine for an app behind sign-in.
- The language switcher (website and app) changes the language for the visitor, including a carer on the quick-log. On the website it sets the cookie; a signed-in parent's choice is also saved with Better Auth `updateUser({ locale })` (see `auth-client.md`, wired with the settings screen).
- Emails and push: sign-up and security emails use `user.locale`. An invitee without an account gets English.

## 4. Translating

Translations are produced by **Languine** (hosted), from the English files.

```bash
pnpm i18n:translate   # translate what changed in English into pl, es, cy
pnpm i18n:check       # every language complete and consistent?
```

1. Edit the English JSON.
2. `pnpm i18n:translate` (reads `LANGUINE_API_KEY` and `LANGUINE_PROJECT_ID` from Infisical folder `/i18n`). It updates the other languages and `languine.lock`.
3. Read the diff. Have a native reader check anything about health, feeding, safety or the clinician reports before release.
4. `pnpm i18n:check`, then commit the catalogs and `languine.lock` together.

`pnpm test` checks what is written (placeholders match English, no markup or email addresses, no unknown keys). `pnpm i18n:check` additionally demands every key exists in every language, so it fails until the translations are generated.

Cost: Languine charges per translated key (English keys times target languages). The free plan is 500 keys, about 160 English keys for three languages; expect the paid plan once the screens exist. The files are plain i18next JSON, so another tool can replace Languine without code changes.

### Add a language

1. Add the code and its own-language name to `app.i18n` in `packages/config/src/app.ts`.
2. Add the folder with the five namespace files (`{}` is fine) and import them in `packages/i18n/src/resources.ts`.
3. Add the language to `languine.json`, run `pnpm i18n:translate`, then `pnpm i18n:check`.
4. Add it to `supportedLocales` in `apps/native/app.json`.
5. Right-to-left languages (Urdu) also need layout work on both platforms; not done yet (see `todos.md`).

## 5. What is not translated

- The API's JSON `message` (clients use `code`).
- Developer-only screens: `/debug` on the website and the test buttons in the app.
- The Novu HTML templates built by `pnpm --filter @repo/emails build` (English only; the live emails are rendered per recipient).
- Brand name and the SEO description in `@repo/config/app`.
